## Requirement

Extend the symptomizer algorithm catalog with per-clinic ownership so a clinic can upload its own private decision-tree algorithm — by selecting a `.json` file in the admin panel — without exposing it to other clinics on the platform.

M2 ships the global shared catalog only (see FR-KT4697 and FR-M3WYNS) with per-clinic enable/disable via `clinic_algorithms`. That model is sufficient for a single-pilot deployment but breaks down the moment a clinic wants a proprietary triage flow (competitive advantage, regulatory carve-out, dialect-specific phrasing) or two clinics onboard with overlapping `algorithm_key`s. This FR adds the orthogonal ownership axis: every algorithm row gains an optional clinic owner; visibility queries filter accordingly; clinic staff upload + delete their own rows through the admin panel.

The upload surface is the **admin panel** (the React SPA at `admin-panel/`, authed by the clinic-user Bearer token on `/api/v1/admin/*`), not the clinic-provisioning surface. Clinic staff log into the panel, open an "Algorithms" page, pick a `.json` file from their machine, and it is uploaded as a private algorithm owned by their clinic. This matches the existing split: the admin panel (Bearer token, role-gated) is the clinic-staff UI; the `/api/v1/clinics/{slug}/*` surface (`X-API-Key`) is for platform provisioning/ops and is intentionally NOT used here. Scripted/bulk upload over the provisioning surface is out of scope for this FR (the same `AlgorithmRepo.insert` is reachable if ops ever needs it).

The same "Algorithms" page also manages **enable/disable** for the clinic — both the platform-global catalog and the clinic's own private uploads. Uploading and enabling are deliberately distinct steps (uploading adds a row the clinic owns; enabling is what surfaces it in walker pre-pick), and the page makes that two-step flow explicit. Because the page lives on the admin (Bearer) surface, this FR adds admin-surface enable/disable endpoints that reuse M2's `ClinicRepo.setAlgorithmEnabled`; the M2 `X-API-Key` enable/disable endpoints on `/api/v1/clinics/{slug}/*` remain unchanged for provisioning/ops.

Deferred from M2 by explicit scope decision on 2026-06-03 — no pilot demand at M2 spec time, M2 vertical slice was already large. Activate this FR when a pilot clinic requests proprietary algorithms or when a second clinic onboards with overlapping algorithm names.

References: FR-KT4697 (algorithm catalog + walker — owns `algorithms` + `clinic_algorithms`), FR-M3WYNS (multi-tenant clinic model + `X-API-Key`), FR-MG7TSR (admin-panel Bearer auth + `TokenClaims`), technical-spec.md § 2.1 (algorithm schema).

## Acceptance Criteria

- AC-A4ZDFW.1: `algorithms` table gains a nullable `owner_clinic_id BIGINT REFERENCES clinics(id) ON DELETE CASCADE` column via a forward migration. NULL = platform-global (preserves all M2 seeded rows verbatim). Non-NULL = owned by exactly one clinic.
- AC-A4ZDFW.2: The unique constraint changes from `(algorithm_key, version)` to `(owner_clinic_id, algorithm_key, version)` so the same `algorithm_key` can coexist as a platform-global row AND as one private row per clinic — no namespace collision between Clinic-A's `headache` and Clinic-B's `headache`.
- AC-A4ZDFW.3: `POST /api/v1/admin/algorithms` accepts a `multipart/form-data` body with **exactly one** file part containing the algorithm JSON (same shape as `core/src/main/resources/algorithms/*.json`); a request with zero or more than one file part is rejected 422. Auth = clinic-user Bearer token; role-gated to `admin` (reuses `requireRole(claims, "admin")`). The handler: (a) enforces a 256KB cap on the file part, (b) parses the JSON, (c) validates via the existing `AlgorithmIngestionValidator`, (d) inserts with `owner_clinic_id = claims.clinicId`. `owner_clinic_id` is read ONLY from token claims, never from the request. Status codes: 401 (no/invalid token), 403 (token role ≠ admin), 413 (file exceeds 256KB), 422 (no/multiple file parts, malformed JSON, or validator rejection), 409 (this clinic already owns `(algorithm_key, version)`), 200 (happy).
- AC-A4ZDFW.4: The admin panel gains an "Algorithms" page (new route in `admin-panel/src/App.tsx` + nav entry in `Layout.tsx`) that lists every algorithm visible to the clinic — platform-global rows AND the clinic's own private rows — each showing its enabled state and, for private rows, an owner marker. The page provides: (a) a `.json` file picker that uploads a private algorithm via the AC-A4ZDFW.3 endpoint, (b) a per-row enable/disable toggle wired to the AC-A4ZDFW.8 endpoints, and (c) a delete control on private rows only, wired to AC-A4ZDFW.6. The page copy makes the upload-vs-enable distinction explicit (a freshly uploaded algorithm is listed but disabled until the clinic enables it). The `ApiClient` (`admin-panel/src/api/client.ts`) is extended to send `multipart/form-data` (it currently sends JSON only). Validator/size/collision errors are surfaced to the user with the server's message; a successful upload, toggle, or delete refreshes the list.
- AC-A4ZDFW.5: Algorithm visibility queries (`ClinicRepo.findEnabledAlgorithmIds(clinicId)`, any future algorithm-listing endpoint) filter rows where `owner_clinic_id IS NULL OR owner_clinic_id = clinicId`. A cross-tenant integration test asserts Clinic-B never sees Clinic-A's private rows under any read path.
- AC-A4ZDFW.6: `DELETE /api/v1/admin/algorithms/{algorithm_key}` removes the calling clinic's private algorithm row (Bearer token, role `admin`). The delete is scoped by `owner_clinic_id = claims.clinicId`, so platform-global rows (`owner_clinic_id IS NULL`) and other clinics' rows are unreachable — a key that resolves to no owned row returns 404. The admin-panel list exposes a delete control. Soft- vs hard-delete decision deferred to implementation time.
- AC-A4ZDFW.7: `AlgorithmSeedLoader` continues to insert JAR-shipped algorithms with `owner_clinic_id = NULL` — no change to the M2 seed path; existing JAR-shipped fixtures remain platform-global.
- AC-A4ZDFW.8: `POST /api/v1/admin/algorithms/{algorithm_key}/enable` and `POST /api/v1/admin/algorithms/{algorithm_key}/disable` toggle enablement for the calling clinic (Bearer token, role `admin`). The handlers resolve `{algorithm_key}` against the clinic's visible set (global OR owned by `claims.clinicId`) and call the existing `ClinicRepo.setAlgorithmEnabled(clinicId, algorithmId, enabled)` — an idempotent upsert into `clinic_algorithms`. `clinicId` comes ONLY from token claims. Status codes: 401 (no/invalid token), 403 (role ≠ admin), 404 (key resolves to no visible algorithm), 200 (happy). The M2 `X-API-Key` enable/disable endpoints on `/api/v1/clinics/{slug}/*` are left unchanged.
- AC-A4ZDFW.9: `GET /api/v1/admin/algorithms` returns the calling clinic's visible algorithm set (Bearer token; readable by any clinic-user role, no `admin` gate). Each entry carries `algorithm_key`, `version`, display name + category (from `metadata`), `enabled` (resolved from `clinic_algorithms`, default `false` when no row exists), and `owned` (`true` when `owner_clinic_id = claims.clinicId`, `false` for platform-global rows). The set is exactly the rows where `owner_clinic_id IS NULL OR owner_clinic_id = claims.clinicId` — the same visibility predicate as AC-A4ZDFW.5, so a clinic never sees another clinic's private rows. Tree bodies are NOT included (list view only). Status codes: 401 (no/invalid token), 200 (happy). This is the endpoint the admin-panel "Algorithms" page (AC-A4ZDFW.4) fetches.

## Technical Design

Builds on technical-spec.md § 2.1, FR-KT4697's algorithm model, and FR-MG7TSR's admin-panel auth.

- **Migration:** `database/0X-migrate-algorithm-ownership.sql` adds the column, drops the existing `algorithms_key_version_uniq` constraint, re-adds it with `owner_clinic_id` in the leading position. Backfill is a no-op (all existing rows stay NULL = global).
- **Model:** `Algorithm` data class gains nullable `ownerClinicId: Long?`. `AlgorithmRepo.insert(algorithm, ingestedBy)` grows an `ownerClinicId: Long? = null` parameter; existing callers (seed loader) pass `null` explicitly. Add `findPrivateByKey(clinicId, key)` / `deletePrivate(clinicId, key)` for the per-clinic delete + resolve paths, and `listVisibleForClinic(clinicId)` returning lightweight summaries (key, version, metadata, `enabled`, `owned`) via a `LEFT JOIN clinic_algorithms` on `(clinic_id, algorithm_id)` filtered by `owner_clinic_id IS NULL OR owner_clinic_id = ?`. The summary projection deliberately omits the `tree` JSONB so the list query stays cheap.
- **Backend routes:** new `GET` (list), `POST` (upload), `DELETE`, and `POST .../enable|disable` handlers in `AdminRoutes.kt` (admin surface, mounted under `/api/v1/admin`), all authed by the existing Bearer-token middleware. The mutating routes (upload/delete/enable/disable) are gated with `requireRole(claims, "admin")`; the `GET` list is readable by any clinic-user role (matching how other read endpoints like `GET /doctors` and `GET /sessions` skip the role gate). This is a deliberate move from the originally-drafted `X-API-Key` clinic-provisioning endpoints — clinic staff act through the admin panel, so both upload and enable/disable belong on the admin surface where the tenant is fixed by `claims.clinicId`. The enable/disable handlers resolve the `{algorithm_key}` to an algorithm id within the clinic's visible set, then delegate to the unchanged M2 `ClinicRepo.setAlgorithmEnabled` — no new persistence logic, just an admin-authed entry point alongside the existing `X-API-Key` one.
- **Multipart handling (new to the backend):** the backend currently handles JSON bodies only — no Ktor route uses `receiveMultipart()` today. The upload handler reads the first file part via `call.receiveMultipart()`, streams it into a bounded buffer that aborts at 256KB (→ 413), then decodes UTF-8 and parses with the existing kotlinx-serialization `Json`. Validation reuses `AlgorithmIngestionValidator` unchanged — the algorithm payload contract is identical between global and private rows. Route-layer additions: the 256KB cap (413) and the per-clinic `(algorithm_key, version)` collision check (409).
- **Admin panel (React SPA):** add an `AlgorithmsPage` under the `<Route element={<Layout />}>` block in `admin-panel/src/App.tsx`, plus a `<NavLink>` in `admin-panel/src/components/Layout.tsx`. The page fetches the clinic's visible algorithms (globals + own private) with their enabled state, renders an `<input type="file" accept="application/json">` picker for new private uploads, a per-row enable/disable toggle, and a delete control on private rows. The list visibly separates "uploaded but disabled" from "enabled" so the two-step nature is obvious. `ApiClient` (`admin-panel/src/api/client.ts`) gains a multipart path: when the body is `FormData`, do NOT set `Content-Type` (let the browser set the boundary) and do NOT `JSON.stringify`; the enable/disable/delete calls stay on the existing JSON/no-body path. Errors render the server's message inline; success refreshes the list. The page's initial fetch and every post-mutation refresh call the `GET /api/v1/admin/algorithms` list endpoint (AC-A4ZDFW.9).
- **Visibility filter:** `ClinicRepo.findEnabledAlgorithmIds(clinicId)` currently joins through `clinic_algorithms`. Extend with `WHERE (a.owner_clinic_id IS NULL OR a.owner_clinic_id = ?)` once `algorithms` is joined. Visibility is enforced at the repo layer, not at the route layer, so every read path inherits the filter.

Open design questions (resolve at implementation time):

- Upload payload size cap — set at 256KB per algorithm (matches the largest M2 ported algorithm with headroom). Enforced as a streaming abort on the multipart part, not a post-read length check, so a malicious large file is rejected before it is fully buffered.
- File-part contract — the single-file-part requirement is now pinned in AC-A4ZDFW.3. Still open: the part's field name, and whether to also accept a raw `application/json` body on the same endpoint (for non-browser callers). The SPA only needs the multipart path.
- Version-bump UX: if a clinic uploads `headache-v1.0.1` while sessions are mid-walk on `headache-v1.0.0`, do those sessions complete on the old tree or migrate? Likely "complete on the old tree" since `sessions.current_algorithm_id` is a FK to a specific row — but worth confirming.
- Audit trail: the existing `ingested_by` column on `algorithms` captures source; for admin-panel uploads, populate it (or a new `uploaded_by_user`) from `claims.clinicUserId` so a clinic-uploaded row is traceable to the staff member who uploaded it.
- Soft- vs hard-delete: hard-delete cascades into `clinic_algorithms` cleanly; soft-delete needs a `deleted_at` column. Default to hard-delete unless a clinic asks for undo.

## Testing

Per testing-spec.md.

- Unit: validator behavior unchanged — existing `AlgorithmIngestionValidatorTest` continues to cover happy + rejection branches. New unit coverage for the 256KB streaming cap (a part one byte over the limit aborts with 413; a part at the limit passes).
- Integration (Testcontainers Postgres): upload happy path (`POST` multipart → row inserted with `owner_clinic_id = clinic.id`); cross-tenant visibility test (Clinic-A uploads `private-headache`, neither Clinic-B's `findEnabledAlgorithmIds` nor Clinic-B's `GET /api/v1/admin/algorithms` returns that id under any combination of enable flags); list-shape test (`GET` returns globals with `owned=false` plus the clinic's private rows with `owned=true`, and `enabled` reflects `clinic_algorithms` including the default-`false` no-row case); collision test (`POST` for an `(algorithm_key, version)` the clinic already owns returns 409).
- Route tests: Ktor `testApplication` covers all status codes for `GET` list (200 / 401), `POST` upload (200 / 401 / 403 / 409 / 413 / 422), `DELETE` (200 / 401 / 403 / 404), and `enable`/`disable` (200 / 401 / 403 / 404, plus an idempotency assertion that re-enabling an enabled algorithm is a no-op 200). Multipart requests are built with the test client's `MultiPartFormDataContent`. Auth/role tests reuse the existing admin Bearer-token fixtures (`AdminFixtures.kt`, `requireRole`) from FR-MG7TSR.
- SPA tests (Vitest): `AlgorithmsPage` renders globals + private rows with their enabled state, sends an upload as a `FormData` body through `ApiClient` (asserting no JSON `Content-Type` is forced), toggles a row and asserts the enable/disable call fires, surfaces a server validation error inline, and refreshes the list on success.
- Migration check: a fresh DB seeded with the M2 JAR algorithms after the migration has all rows with `owner_clinic_id IS NULL`; the existing walker exhaustive-walk test passes unchanged.

## Notes

- This FR was deferred from M2 by explicit scope decision on 2026-06-03 driven by lack of pilot demand and M2's already-large surface area. M2's per-clinic customizability is limited to (a) enable/disable of the shared catalog, (b) `default_language` + `allowed_languages`, (c) free-form `clinics.config` JSONB.
- **Upload surface changed 2026-06-18:** the clinic-facing upload moved from the originally-drafted `POST /api/v1/clinics/{slug}/algorithms` (`X-API-Key`, JSON body) to `POST /api/v1/admin/algorithms` (Bearer token, multipart file upload) so clinic staff can upload `.json` files directly in the admin panel. The ownership model (column, constraint, visibility filter) is unchanged.
- The `clinic_algorithms` enable/disable join from M2 is orthogonal to ownership — a clinic must still explicitly enable a private algorithm via `setAlgorithmEnabled` for it to surface in walker pre-pick. Uploading is not the same as enabling; the admin-panel "Algorithms" page should make this two-step nature obvious (upload, then enable).
- This is the backend's first multipart endpoint — `receiveMultipart()` is new infrastructure, and `ApiClient` gains its first non-JSON request path. Both are noted as net-new surfaces, not reuse.
- Confidence threshold customization per clinic (`clinics.config.llm.confidence_threshold`) is a separate documented-but-unimplemented gap from FR-PWVTT4 — not in scope here.
