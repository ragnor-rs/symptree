## Requirement

Ship the **clinic-admin panel** — the project's first frontend — as a **Vite SPA** consuming the FR-MG7TSR REST surface (project-owner decision 2026-06-11). For the pilot it lets a clinic admin log in, manage doctors (with their symptomizer specialist codes, weekly working hours, and days off), view per-patient symptomizer results, and see/cancel bookings. It is decoupled from `core` exactly like the bot module — no compile-time dependency, talks over HTTP only.

This is new scope: requirements.md § 5 declared the admin web UI "not out-of-scope … a candidate for a later milestone once a frontend module exists." This FR creates that module. Operator↔patient chat is explicitly **deferred** (fast-follow), but the panel's information architecture leaves room for a future "Conversations" section.

References: FR-MG7TSR (the REST surface + auth token this consumes); FR-YDANPW (doctor/schedule model rendered); FR-W03362 (bookings shown); requirements.md § 2.2 (i18n — the panel is RU + KK), § 5 (admin web UI candidacy); brainstorm 2026-06-11 (Vite SPA + REST, must-have screens: doctors+schedules, results view).

## Acceptance Criteria

- AC-XKH348.1: A new top-level `admin-panel/` module: Vite + React + TypeScript (pinned in the module's `package.json`, recorded in a technical-spec ADR). It builds via `npm run build` to static assets. **Amendment (2026-06-15, project-owner decision):** it *is* a Gradle module — a `base`-plugin `build.gradle.kts` drives `npm ci`/`build`/`test` via `Exec` tasks wired to the lifecycle, so `./gradlew build` builds it and `./gradlew test` runs its suite — but it has **no Kotlin/compile-time coupling** to `core`/`messaging` (HTTP-only at runtime; the root build excludes it from the Kotlin/detekt plugins). `.gitignore` excludes `admin-panel/node_modules` + `admin-panel/dist`.
- AC-XKH348.2: Login screen → `POST /api/v1/admin/login`; the bearer token is held in memory (or `httpOnly` cookie if the token transport is cookie-based per FR-MG7TSR's ADR) and attached to every subsequent API call; 401 responses route back to login; logout clears the token.
- AC-XKH348.3: Doctors screen — list (active + a soft-deleted toggle), create, edit (`full_name`, `specialist_codes` chosen from the clinic's enabled algorithms' specialist codes, `slot_minutes`, `active`), soft-delete. Specialist-code selection is driven by data from the API, not a hardcoded list. **Amendment (2026-06-15):** MG7TSR exposed no specialist-code source to the admin token, so this FR added `GET /api/v1/admin/specialist-codes` (deduped semantic codes from the clinic's enabled algorithms) to drive the dropdown.
- AC-XKH348.4: Schedule editor per doctor — weekly hours as a 7-day grid supporting split shifts (multiple intervals per day; empty day = day off) saved via `PUT …/weekly-hours`; a time-off list (add/remove date-range absences) via the time-off endpoints. Client-side validation mirrors the server's `end > start` / no-overlap rules and surfaces the server's 422 message on failure. **Amendment (2026-06-15):** the grid loads the doctor's persisted hours via `GET …/weekly-hours` (added — the editor no longer opens empty / can't silently wipe a schedule). Day numbering follows the backend canonical **0=Sun..6=Sat** (`EXTRACT(DOW)` / DB `CHECK BETWEEN 0 AND 6`); the original SPA used 1–7 which broke Sunday. The grid's **first day is per-clinic** (`config.preferences.first_day_of_week`, **default Monday**) read via `GET /api/v1/admin/clinic-settings` — display ordering only, the stored values stay 0–6.
- AC-XKH348.5: Symptomizer-results section — paginated session list (patient ref, language, status, time) via `GET …/sessions`; a detail view (`GET …/sessions/{id}`) rendering the walked Q→A path + conclusion (urgency badge, recommended specialist, tests, prep notes). Read-only. **Amendment (2026-06-15):** the MG7TSR detail surface carried no conclusion, so this FR added a semantic `conclusion` block to `GET …/sessions/{id}` (urgency/clinic-action/specialist codes + algorithm-localized diagnosis/action/tests) — see Technical Design.
- AC-XKH348.6: Bookings section — list (doctor, slot, status, feedback score) via `GET …/bookings`; cancel action (`PATCH …/bookings/{id}` with reason) with a confirm dialog.
- AC-XKH348.7: The panel UI is localized RU + KK (requirements § 2.2) via a frontend i18n bundle; language toggle persists per user. No hardcoded user-facing Cyrillic literals in components — strings come from the bundle.
- AC-XKH348.8: All clinic-scoped data shown is exactly what the authenticated token's clinic owns — the SPA never sends a `clinic_id`; the server derives it from the token (FR-MG7TSR AC-MG7TSR.3). A logged-in admin of clinic A can never view clinic B's doctors/sessions/bookings (enforced server-side; the SPA simply has no affordance to attempt it).
- AC-XKH348.9: A documented local-dev + build path: `admin-panel/README.md` covers install, dev server (proxying `/api` to a local `core`), and production build; the build output is servable as static files (by `core` or any static host — deployment topology recorded in technical-spec).

## Technical Design

Builds on FR-MG7TSR (REST + auth), brainstorm 2026-06-11.

- **Topology:** `admin-panel/` is a sibling of `core/` + `messaging/`, mirroring the bot↔core decoupling — HTTP only, no shared build. Framework choice (React vs Svelte) is pinned in an ADR; either is acceptable, default React + TypeScript + Vite for ecosystem/hiring.
- **Auth handling:** token from `POST /admin/login`; a fetch wrapper attaches `Authorization: Bearer …` and centralizes 401 → login redirect. If FR-MG7TSR's ADR lands on `httpOnly` cookies instead of an in-memory bearer, the wrapper omits the header and relies on the cookie — the FRs share one ADR so this stays consistent.
- **i18n:** a lightweight frontend catalog (e.g. `react-i18next` or a hand-rolled map) with `ru` + `kk` bundles, parallel to the backend catalog keys where they overlap (conclusion rendering reuses backend-provided localized text; chrome is frontend-bundled).
- **Backend additions (amendment 2026-06-15, supersedes the original "no new backend coupling"):** MG7TSR's surface under-delivered two reads this FR's ACs require, so two **additive read endpoints** were added to `core`'s admin surface, both emitting **semantic DTOs only** (FR-VWRNDR — urgency/clinic-action/specialist as codes; algorithm-authored diagnosis/action/tests localized by `core` to the session language; SPA owns chrome):
  - `GET /api/v1/admin/sessions/{id}` now carries a `conclusion` block for concluded sessions (reconstructed from the session's algorithm + terminal `ConclusionNode`). Powers AC-XKH348.5.
  - `GET /api/v1/admin/specialist-codes` returns the clinic's enabled algorithms' specialist codes (deduped, sorted). Powers AC-XKH348.3.
  The panel remains a pure HTTP client with no compile-time dependency on `core`. Serving the built assets (from `core` via a static route, or a separate static host) is a deployment decision recorded in technical-spec § 1.
- **Build integration (amendment 2026-06-15):** `admin-panel` is a Gradle module (mirrors MMP `frontend`) — `base` plugin + `Exec` tasks (`npm ci`/`build`/`test`) wired to `assemble`/`check`, excluded from the root Kotlin/detekt plugins. `./gradlew build` builds the SPA and `./gradlew test` runs its Vitest suite, so the panel is part of the project gate. No Kotlin/compile coupling; HTTP-only at runtime.

## Testing

Per testing-spec.md (frontend testing conventions to be added to testing-spec under this FR).

- Component tests (Vitest + Testing Library or framework equivalent) for the doctor form, schedule grid (split-shift add/remove, validation), and the session-detail renderer.
- A fetch-wrapper test asserting `Authorization` attachment + 401→login redirect, against a mocked API.
- i18n bundle completeness test: every key present in `ru` exists in `kk` and vice versa (mirrors backend `MessageCatalogConsistencyTest`).
- Manual smoke checklist (login → create doctor → set hours → see a seeded session result → cancel a booking) against a local `core` before pilot — recorded in `admin-panel/README.md`.
- **Amendment (2026-06-15):** the SPA **is** part of the `./gradlew test` gate (via the `admin-panel` Gradle module's `Exec`-driven `test` task); `npm test` runs the same Vitest suite directly. Backend additions are tested in `core` under the Kotlin gate (`SessionConclusionRoutesTest`, `SpecialistCodesRoutesTest`).

## Notes

- Operator↔patient chat is deferred; the IA reserves a "Conversations" slot. When it lands it adds a WebSocket/SSE client + a BOT↔OPERATOR handover toggle, consuming a future messaging-module surface.
- Framework choice is deliberately left to an ADR rather than hardcoded in the FR so the implementer can pick based on team familiarity; the FR's ACs are framework-agnostic.
- Multi-source doctor federation (internal + HL7/CRM) surfaces in this panel later via FR-YDANPW's `DoctorDirectory` aggregation + the manual-dedup merge UI — the doctors screen is built to render a `source` badge per doctor from day one even though MVP shows only `INTERNAL`.
- A separate CI FR should add the SPA build + test to the pipeline; M2 gates only the Kotlin modules.
