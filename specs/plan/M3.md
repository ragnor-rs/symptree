**Deferred from M2 (FR-YDANPW re-scope, 2026-06-11 owner decision) — multi-source federation runtime:** M2/FR-YDANPW shipped the `MedicalDataSource` abstraction, the canonical doctor catalog schema, and the `INTERNAL` source only (`SourceKind { INTERNAL }`, single-source `DataSourceRegistry`). The following build on that seam in M3:

- **Source-kind taxonomy beyond `INTERNAL`** — add `HL7V2` (a standard-format kind: one adapter backs many HIS instances via `connection_params`) and per-integration CRM kinds (no generic `REST_CRM` — each non-standard CRM is its own kind + adapter). Each kind's adapter lives in its own `source/<kind>/` subpackage; provider names are confined there (`NoProviderNameLeakTest` sweeps `source/` excluding those subpackages). — FR-TNWP9R / FR-2VQ7CA
- **Persisted source registry** — `sources(id, clinic_id, kind, connection_params JSONB, …)`; build `DataSourceRegistry` from rows, switching on `kind` to instantiate the right adapter with parsed params. — FR-2VQ7CA
- **Multi-source federation behavior** — `listAllDoctors` across ≥2 sources, cross-source booking routing, directory-less sources contributing zero, full→incremental directory sync (uses the `synced_at`/`sync_cursor`/`deleted_at` columns already shipped in M2). The multi-source/multi-kind `DataSourceRegistryTest` scenarios trimmed from M2 land here. — FR-2VQ7CA
- **Manual cross-source doctor-identity dedup** — merge/unmerge actions on `doctor_identity` (sync-stable: re-points rows, never deletes synced source rows). — FR-2VQ7CA
- Forward design (kind = adapter+params discriminator; `SourceId` per-instance PK; `connection_params` model) is recorded in technical-spec.md § 3.4.
